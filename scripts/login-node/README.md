# Login node user onboarding

This directory contains the administrator workflow for adding non-privileged
users to the login node. Linux and Kubernetes access are intentionally
separate:

- SSH uses a Linux account and an individual SSH key.
- Kubernetes uses an individual ServiceAccount and restricted namespace RBAC.
- Users are not given `sudo` or the cluster administrator kubeconfig.

The examples below onboard `mluser1` to the login node at
`44.203.188.20` and grant access to submit Kubeflow `TrainJob` resources in
the `mlproject` namespace.

## 1. Create the Linux account and SSH key

Run the script directly on the login node from a checkout of this repository:

```bash
sudo ./scripts/login-node/01-create-login-user.sh mluser1
```

The script:

1. Creates `/home/mluser1` with `/bin/bash` as the login shell.
2. Does not add the account to `sudo` or another privileged group.
3. Generates a passphrase-protected Ed25519 key pair under
   `/root/login-user-keys/mluser1/`.
4. Adds the public key to `/home/mluser1/.ssh/authorized_keys`.
5. Creates `/home/mluser1/.kube` without installing credentials.

The generated files are:

```text
/root/login-user-keys/mluser1/id_ed25519      # private key
/root/login-user-keys/mluser1/id_ed25519.pub  # public key
```

The private key must never be committed, emailed, pasted into chat, or left in
a location readable by other users.

## 2. Transfer the private key

On the login node, temporarily make the private key available to the existing
administrative SSH account:

```bash
sudo cp \
  /root/login-user-keys/mluser1/id_ed25519 \
  /home/ubuntu/mluser1-id_ed25519
sudo chown ubuntu:ubuntu /home/ubuntu/mluser1-id_ed25519
sudo chmod 0600 /home/ubuntu/mluser1-id_ed25519
```

On the administrator workstation, copy it through SSH and protect it:

```bash
scp \
  -i ~/.ssh/terraform-user \
  ubuntu@44.203.188.20:/home/ubuntu/mluser1-id_ed25519 \
  ~/.ssh/mluser1-id_ed25519
chmod 0600 ~/.ssh/mluser1-id_ed25519
```

The `.pub` file cannot be used with `ssh -i`; that option requires the private
key without the `.pub` suffix.

Test the new account:

```bash
ssh -i ~/.ssh/mluser1-id_ed25519 mluser1@44.203.188.20
```

After a successful login, remove both server-side copies of the private key:

```bash
sudo rm /home/ubuntu/mluser1-id_ed25519
sudo rm /root/login-user-keys/mluser1/id_ed25519
```

The installed public key and the root-owned backup of the public key may
remain.

Verify that the new account is not privileged:

```bash
whoami
id
sudo -n true
```

The final command must fail because the user has not been granted `sudo`.

## 3. Provision Kubernetes access through Argo CD

Argo CD recursively manages `argocd/applications/mlprojects/`. The shared Role
is defined in:

```text
argocd/applications/mlprojects/03-job-submitter-role.yaml
```

It permits users to:

- Create, inspect, watch, and delete Kubeflow `TrainJob` resources.
- Inspect Pods, logs, and events generated by their training jobs.
- Inspect Kueue `LocalQueue` and `Workload` resources.

It does not permit direct Pod creation, Secret access, or RBAC administration.

The resources for `mluser1` are defined in:

```text
argocd/applications/mlprojects/users/mluser1.yaml
```

That manifest creates the `mluser1` ServiceAccount and binds it to the shared
Role in `mlproject`. To onboard another user, copy the file and replace every
occurrence of `mluser1` with the new Linux username.

Commit and push these manifests, then wait for the `applications` Argo CD
Application to synchronize. Verify the result with the administrator
kubeconfig:

```bash
kubectl -n mlproject get serviceaccount mluser1
kubectl -n mlproject get role kubeflow-cpu-job-submitter
kubectl -n mlproject get rolebinding mluser1-kubeflow-submitter
```

Verify the effective permissions:

```bash
kubectl auth can-i create trainjobs.trainer.kubeflow.org \
  --as=system:serviceaccount:mlproject:mluser1 \
  --namespace=mlproject

kubectl auth can-i create pods \
  --as=system:serviceaccount:mlproject:mluser1 \
  --namespace=mlproject

kubectl auth can-i get secrets \
  --as=system:serviceaccount:mlproject:mluser1 \
  --namespace=mlproject
```

The expected answers are `yes`, `no`, and `no` respectively.

## 4. Remaining step

The ServiceAccount does not automatically create a user kubeconfig. Generate
the credential separately after Argo CD has created the account, and install
only the restricted kubeconfig at `/home/mluser1/.kube/config`. Never copy
`/etc/kubernetes/admin.conf` or `/home/ubuntu/.kube/config` into a user home
directory.
