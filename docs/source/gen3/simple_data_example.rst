GEN3 Simple Data Curation Example
=================================

This page demonstrates the concepts in :doc:`data_curation_guide` with two
fictional participants. It deliberately uses only five domain nodes so that
the relationships remain easy to follow::

   case -> demographic
      `-> sample -> aliquot -> vcf_file

The property names and dictionary fragments below are educational examples.
A real submission must use templates and link names generated by the
dictionary installed in the target GEN3 commons.

1. Raw source data
------------------

Assume a laboratory sends one CSV file and two VCF files. The CSV is convenient
for the laboratory but is not yet arranged as GEN3 graph metadata.

``laboratory_export.csv``::

   patient_id,diagnosis,body_site,sex,birth_year,race,sample_id,sample_type,collection_method,collection_date,aliquot_id,analyte_type,volume_ul,concentration_ng_ul,vcf_path,genome_build
   P001,Cancer,Blood,F,1970,Asian,S001,Blood,Venipuncture,2026-07-01,A001,DNA,50,25.4,raw/P001.vcf,GRCh38
   P002,Healthy Control,Saliva,M,1982,White,S002,Saliva,Saliva collection kit,2026-07-02,A002,DNA,40,19.8,raw/P002.vcf,GRCh38

The two raw data files contain genomic variants. A highly abbreviated
``P001.vcf`` might look like::

   ##fileformat=VCFv4.2
   ##reference=GRCh38
   #CHROM  POS     ID  REF  ALT  QUAL  FILTER  INFO
   1       10177   .   A    AC   100   PASS    .

The corresponding ``P002.vcf`` might contain::

   ##fileformat=VCFv4.2
   ##reference=GRCh38
   #CHROM  POS     ID  REF  ALT  QUAL  FILTER  INFO
   2       20001   .   G    T    99   PASS    .

GEN3 does not automatically turn the VCF rows into searchable metadata. The
VCF files remain downloadable raw data objects. The CSV columns are curated
into node records, while each VCF is uploaded to object storage and registered
in Indexd.

2. Curated metadata
-------------------

The flat laboratory row is separated into five related concepts:

.. list-table:: Source fields assigned to GEN3 nodes
   :header-rows: 1
   :widths: 20 35 45

   * - Node
     - Source fields
     - Purpose
   * - ``case``
     - ``patient_id``, ``diagnosis``, ``body_site``
     - Describes the participant or case.
   * - ``demographic``
     - ``sex``, ``birth_year``, ``race``
     - Describes participant demographics.
   * - ``sample``
     - ``sample_type``, ``collection_method``, ``collection_date``
     - Describes the collected biological material.
   * - ``aliquot``
     - ``analyte_type``, ``volume_ul``, ``concentration_ng_ul``
     - Describes a portion derived from the sample.
   * - ``vcf_file``
     - derived file name, ``genome_build``, and file format
     - Describes the registered VCF object.

Identifiers and standard submission fields are added during curation. For
example, raw patient ID ``P001`` becomes stable submitter ID
``demo-case-P001``. All records belong to project ``DEMO-STUDY1``.

3. The five node types
----------------------

This example uses the following node types and records:

.. list-table:: Example node records
   :header-rows: 1
   :widths: 18 30 52

   * - Node type
     - Example record
     - Meaning
   * - ``case``
     - ``demo-case-P001``
     - Participant P001.
   * - ``demographic``
     - ``demo-demographic-P001``
     - Demographic information for P001.
   * - ``sample``
     - ``demo-sample-S001``
     - The blood sample collected from P001.
   * - ``aliquot``
     - ``demo-aliquot-A001``
     - A DNA aliquot derived from S001.
   * - ``vcf_file``
     - ``demo-vcf-P001``
     - Metadata for P001's registered VCF file.

The same five node types are reused for P002. A dictionary defines each node
type once; the TSV files can then submit many records of that type.

4. Three properties for each node
---------------------------------

For clarity, each node has only three domain properties:

.. list-table:: Example domain properties
   :header-rows: 1
   :widths: 20 25 25 30

   * - Node
     - Property 1
     - Property 2
     - Property 3
   * - ``case``
     - ``disease_type``
     - ``primary_site``
     - ``consent_group``
   * - ``demographic``
     - ``gender``
     - ``year_of_birth``
     - ``race``
   * - ``sample``
     - ``sample_type``
     - ``collection_method``
     - ``collection_date``
   * - ``aliquot``
     - ``analyte_type``
     - ``volume_ul``
     - ``concentration_ng_ul``
   * - ``vcf_file``
     - ``file_name``
     - ``data_format``
     - ``genome_build``

System and relationship fields such as ``type``, ``submitter_id``,
``project_id``, ``object_id``, and ``cases.submitter_id`` are not counted
among the three domain properties.

5. Links between node records
-----------------------------

The first participant's records form this graph::

   Case: demo-case-P001
      |-- Demographic: demo-demographic-P001
      `-- Sample: demo-sample-S001
             `-- Aliquot: demo-aliquot-A001
                    `-- VCF file: demo-vcf-P001

The links are represented in the child TSV records:

.. list-table:: Example parent links
   :header-rows: 1
   :widths: 25 35 40

   * - Child node
     - Link column
     - Parent value
   * - ``demographic``
     - ``cases.submitter_id``
     - ``demo-case-P001``
   * - ``sample``
     - ``cases.submitter_id``
     - ``demo-case-P001``
   * - ``aliquot``
     - ``samples.submitter_id``
     - ``demo-sample-S001``
   * - ``vcf_file``
     - ``aliquots.submitter_id``
     - ``demo-aliquot-A001``

The P002 records use the same link pattern with their own identifiers. Parent
records must be submitted before their children.

6. Example data dictionary
---------------------------

A production GEN3 dictionary normally contains one YAML file per node, common
schema references, system properties, and formal link definitions. The
following abbreviated files show the important parts of this example. They
are explanatory fragments, not a buildable production dictionary.

``case.yaml``::

   $id: case
   title: Case
   category: administrative
   type: object
   properties:
     disease_type:
       type: string
       enum: [Cancer, Healthy Control, Not Reported]
     primary_site:
       type: string
       enum: [Blood, Saliva, Not Reported]
     consent_group:
       type: string
       enum: [General Research Use]
   required: [disease_type, primary_site, consent_group]

``demographic.yaml``::

   $id: demographic
   title: Demographic
   category: clinical
   type: object
   properties:
     gender:
       type: string
       enum: [Female, Male, Not Reported]
     year_of_birth:
       type: integer
     race:
       type: string
   links:
     - name: cases
       target_type: case
       multiplicity: many_to_one
   required: [gender, year_of_birth, race]

``sample.yaml``::

   $id: sample
   title: Sample
   category: biospecimen
   type: object
   properties:
     sample_type:
       type: string
       enum: [Blood, Saliva]
     collection_method:
       type: string
     collection_date:
       type: string
       format: date
   links:
     - name: cases
       target_type: case
       multiplicity: many_to_one
   required: [sample_type, collection_method, collection_date]

``aliquot.yaml``::

   $id: aliquot
   title: Aliquot
   category: biospecimen
   type: object
   properties:
     analyte_type:
       type: string
       enum: [DNA, RNA]
     volume_ul:
       type: number
     concentration_ng_ul:
       type: number
   links:
     - name: samples
       target_type: sample
       multiplicity: many_to_one
   required: [analyte_type, volume_ul, concentration_ng_ul]

``vcf_file.yaml``::

   $id: vcf_file
   title: VCF File
   category: data_file
   type: object
   properties:
     file_name:
       type: string
     data_format:
       type: string
       enum: [VCF]
     genome_build:
       type: string
       enum: [GRCh38]
   links:
     - name: aliquots
       target_type: aliquot
       multiplicity: many_to_one
   required: [file_name, data_format, genome_build]

The real data-file node would also use common file properties such as
``object_id``, ``file_size``, and ``md5sum``. The exact syntax for common
references, link definitions, categories, and constraints must match the
baseline dictionary used to build the commons.

7. Final metadata for two data items
------------------------------------

After curation, the two source rows become five submission TSV files. Each
file contains two records: one for P001 and one for P002. The examples use
spaces for visual alignment, but the actual files must contain tab-separated
columns.

``case.tsv``::

   type  submitter_id    project_id  disease_type     primary_site  consent_group
   case  demo-case-P001  DEMO-STUDY1 Cancer           Blood         General Research Use
   case  demo-case-P002  DEMO-STUDY1 Healthy Control  Saliva        General Research Use

``demographic.tsv``::

   type         submitter_id          project_id  cases.submitter_id  gender  year_of_birth  race
   demographic  demo-demographic-P001 DEMO-STUDY1 demo-case-P001      Female  1970           Asian
   demographic  demo-demographic-P002 DEMO-STUDY1 demo-case-P002      Male    1982           White

``sample.tsv``::

   type    submitter_id     project_id  cases.submitter_id  sample_type  collection_method       collection_date
   sample  demo-sample-S001 DEMO-STUDY1 demo-case-P001      Blood        Venipuncture             2026-07-01
   sample  demo-sample-S002 DEMO-STUDY1 demo-case-P002      Saliva       Saliva collection kit    2026-07-02

``aliquot.tsv``::

   type     submitter_id      project_id  samples.submitter_id  analyte_type  volume_ul  concentration_ng_ul
   aliquot  demo-aliquot-A001 DEMO-STUDY1 demo-sample-S001      DNA           50         25.4
   aliquot  demo-aliquot-A002 DEMO-STUDY1 demo-sample-S002      DNA           40         19.8

Before creating the file metadata, assume the two VCFs have been uploaded and
Indexd has returned fictional GUIDs ``dg.DEMO/1111`` and ``dg.DEMO/2222``.

``vcf_file.tsv``::

   type      submitter_id  project_id  aliquots.submitter_id  object_id     file_name  data_format  genome_build
   vcf_file  demo-vcf-P001 DEMO-STUDY1 demo-aliquot-A001      dg.DEMO/1111  P001.vcf   VCF          GRCh38
   vcf_file  demo-vcf-P002 DEMO-STUDY1 demo-aliquot-A002      dg.DEMO/2222  P002.vcf   VCF          GRCh38

Submit the files in dependency order::

   case.tsv
      -> demographic.tsv
      -> sample.tsv
           -> aliquot.tsv
                -> vcf_file.tsv

``demographic.tsv`` and ``sample.tsv`` can be submitted in either order after
``case.tsv`` because neither depends on the other. Sheepdog validates every
record against the installed dictionary and resolves each link to an existing
parent record.

The resulting graph contains ten domain records::

   demo-case-P001
      |-- demo-demographic-P001
      `-- demo-sample-S001
             `-- demo-aliquot-A001
                    `-- demo-vcf-P001

   demo-case-P002
      |-- demo-demographic-P002
      `-- demo-sample-S002
             `-- demo-aliquot-A002
                    `-- demo-vcf-P002

This graph metadata is stored through Sheepdog, while the two raw VCF objects
remain in object storage and their locations and GUIDs are managed through
Indexd. Tube can subsequently flatten selected graph properties into
Elasticsearch for Guppy and the Portal.
